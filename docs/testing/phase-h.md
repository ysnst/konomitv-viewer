# フェーズH シーク後の字幕同期ずれの再発時確認

基準版はIPA0.20/build20、完全SHA `8ed991fd334f56685bf57fc2c80654eb5fa2b4df`。ユーザー実機結果は[device-0.20.md](device-0.20.md)。字幕残留は解消済み。シーク後の表示タイミングずれは別件で、方向/秒数/条件が不明。

フェーズHのソース調査だけでは実機現象の原因を特定できず、実行コード・時刻変換・描画周期・Gの残留防止は変更していない。新しい通常版/診断版IPAも作成していない。

詳しい調査根拠と検証結果は[字幕同期ずれの調査報告](../subtitle-sync-investigation.md)を参照。追加情報を得た段階で調査を再開する。

## 次回発生時に確認する情報

一度に多数の条件を変えず、同じ番組・字幕・画質で確認する。サーバーの録画全体を事前取得しない。

| 項目 | 記録する内容 |
| --- | --- |
| 時刻差 | 字幕が早い/遅い、概算秒数、一定/増大/自然復旧 |
| 操作 | タップ/ドラッグ/10秒戻る/30秒進む、前方/後方、前後の再生位置 |
| 区間 | 再生済み/未再生、短距離/長距離、可能ならsegment境界 |
| 状態 | 再生中/一時停止中、速度、画質、バッファ表示の有無 |
| 表示 | 通常/全画面、PiPの前後、バックグラウンド復帰の有無 |
| 再現性 | 同じ操作を同じ位置で繰り返すと起きるか |
| 復旧 | そのまま継続、一時停止→再開、同位置へ再シーク、プレイヤー再起動を区別 |
| 素材/環境 | 利用サーバーの版、素材のフレームレートなど既知の情報 |

可能なら音声を含む短い画面録画でシーク前後を比較する。画面録画自体の遅延もあり得るので、これだけで内部PTSの差を断定しない。認証情報や不要な個人情報を含めない。写真/両方保存は別の未確認項目で、今回の「接続と保存」成功から推定しない。

## 内部診断を追加する場合の設計案（未実装）

0.20には字幕時刻を取り出す診断モード/共有機能がない。LiveContainerの通常ログだけで以下を取得できるとは扱わない。再現条件で絞れなければ、別の診断用IPAを実装・レビュー・ビルドしてから使用する。

- 初期OFFの明示的診断モード。既存の更新/シーク/受信イベントからだけ記録し、新しい高頻度タイマーを回さない。
- 最大512件のメモリリング、最大128KiBのエクスポート1件を上限案とし、古い記録を捨てる。無制限の永続ログは作らない。具体的な寸法/負荷は実装時に検証する。
- 無作為なセッション識別子、単調時刻、再生/シーク世代、要求位置、VLC報告位置/状態/isSeeking、再生速度、完了/バッファ状態の変化、segment番号/範囲、抽出PTS、字幕位置変換値、fallback使用有無、描画呼出位置/時刻を記録候補とする。
- 取得TSの先頭videoPTSを「表示フレームPTS」と呼ばない。現在の公開出力経路で表示映像/再生音声のPTSは未取得。取得できない欄はnull/未取得として残し、要求位置から捏造しない。
- タイトル・字幕本文・画像・URL・HTTPヘッダー・トークン・ユーザーIDは記録しない。描画中の文字列整形/ディスクI/Oを避け、書式化と出力を背景へ分ける。
- アプリの領域内で一時出力し、iOS共有シートで「ファイルに保存」。診断終了/明示削除で消す。LiveContainerのゲスト領域/共有動作は実機未確認で、ホストのConsole接続を前提にしない。

これは将来の診断方法の提案であり、現在の0.20で操作できる手順ではない。通常時はOFFなら記録しない設計にするが、CPU/メモリ/保存/発熱の実測値を先に保証しない。

## 原因候補を分ける順序

1. 目視のずれ方向/量と継続性を確認する。
2. 要求位置、完了通知時のVLC位置、再生再開後のVLC位置を別々に照合する。
3. 受信TSのPTS→字幕位置変換とプレイリスト時刻を照合する。
4. fallback、部分受信、重複/遅着、VLC補間時計、バッファリングを区別する。
5. 根拠を得た箇所だけ修正し、Gの残留防止と0.20成功16件を再検証する。

H.264素材の新規準備、PiP内字幕/実況、全編の先行取得、固定時間補正は対象外。
