# 録画ホームと履歴表示

## 進捗の読み取り

`WatchedHistoryStore` は `/api/settings/client` を一括取得し、番組 ID、最後の再生位置、更新日時だけを表示用スナップショットへ保持する。同時読み取りは一つの Task に合流する。各 `VideoCell` は通知を受け、番組 ID と `recorded_video.duration` から同期的にバーを更新する。セルから通信しない。

認証世代、同期世代、認証設定世代、接続先 URL をキャッシュの有効範囲とする。設定変更通知が届く前でも getter が現在の範囲を照合する。ログアウト・同期 OFF・アカウント変更・接続先変更では旧キャッシュを表示しない。PUT 成功後は読み取り世代を進め、保存前に始まった GET の遅い応答を捨てる。同一範囲の更新では前回表示を保ち、履歴一覧の取得が保存と重なった場合は一度だけ新しい取得へ合流する。

表示中の一覧がある間だけ30秒 Timer を動かす。弱参照の利用者がなくなるか、シーンが非アクティブになれば停止する。画面復帰と明示更新でも取り直す。

保存側の `ClientSettingsSaveQueue`、最新設定の GET → 対象項目の変更 → PUT、422時の再試行は維持する。改造サーバーの `reportWatched` / `watched_ratio` は最大到達位置の機能として残し、PWA の進捗計算には使わない。

## ホームの取得と画面

`VideoHomeViewController` は既存の `VideoCell`、`SPHeaderView`、各一覧とプレイヤーを使用する。新着は録画 API の1ページ（最大30件）から10件、マイリストと履歴は ID 指定 API の1ページから各4件を表示する。空 IDs では通信しない。録画全体のページ走査はしない。

マイリストは既存の同期ストアで未送信変更との整合性を保つ。履歴は共有スナップショットを使う。マイリスト同期と履歴読み取りはそれぞれ一括処理であり、番組単位の設定 API 呼び出しは行わない。ID 指定は本家と同様に登録 ID を渡すため、ID の登録数が非常に大きい場合の URL 長制限は残る。

ホーム表示中の30秒更新、明示更新、復帰、履歴・マイリスト通知を一つの更新 Task へまとめ、更新中の要求は一回だけ保留する。非表示・非アクティブ時は Timer と Task を停止する。反映前に画面世代と接続・認証範囲を照合する。更新時は現在の先頭可視番組を目印にしてスクロール位置を維持する。

サムネイル・局ロゴは可視行だけ取得し、取得中 Task と上限付き NSCache を共有する。同一番組が複数セクションにある場合も一回の取得で可視行へ反映する。失敗した画像は次回更新時に再試行する。接続・認証範囲の変更では画像と番組を破棄する。

## 検索と既存フィルタ

検索は標準 `/api/videos/search` に query・order・page を渡し、30件単位のページ送りを維持する。日本語入力の確定を待ち、300ms の間引きと検索語の応答照合を行う。`+`、`&` 等はクエリとして符号化する。

ホームからの検索では既存の録画一覧コントローラーを検索欄が開いた状態で使い、前回のフィルタ・ページ・スクロール位置は適用しない。この一時的な検索画面からは、通常一覧の保存済み表示設定を上書きしない。

既存の未視聴・保護フィルタは改造サーバーの項目を使う従来の端末側判定を維持する。このフィルタを明示的に使う場合の最大50ページ取得と1500件上限は既存の制約として残る。通常検索やホームの初期表示ではこの処理を起動しない。フィルタと検索を併用する場合も、サーバー検索で絞ったページだけを対象にする。

## 検証境界

Foundation の履歴モデル・取得競合は `scripts/HistoryStoreTests.swift` で制御通信を使って検証する。アプリ全体は Actions の iOS 向け Release ビルドと IPA 来歴照合を行う。UIKit 画面の描画、実サーバーの性能・通信、LiveContainer 上の再生・双方向同期は実機確認が必要であり、ビルドや制御通信テストで確認済みとはしない。

## ページ送りと新規遷移（0.6 後）

新しい一覧はページ1・先頭・一時フィルタなしで生成する。並び順のみ従来の保存キーから引き継ぐ。既存キー内のページやスクロールは新規画面へ適用しない。タブ/再生からは同じ画面インスタンスへ戻り、ページ・条件・位置を保持する。マイリスト/履歴の復帰時取得も同じページを使う。

端末設定「ページ切り替え時に先頭へ移動」は未設定時ON。フェーズFではONをヘッダー・上部ページ送りを含む画面全体の最上部とする。OFFは明示操作前に上/下の操作元ページネーションの画面内座標を控え、成功後の確定レイアウトで現在offsetへ実座標差を足して復元する。これによりページごとのカード総高が異なっても同じpagerから続けて操作できる。テーブル外の固定pagerや通常更新では従来のoffset/inset保持を使う。短いページのみ有効範囲へclampする。固定遅延や再補正タイマーは追加しない。

現在ページ最大30行の確定高と幅/選択状態/番組更新単位のキャッシュを維持する。画像は固定枠への代入で行高を変更しない。PaginationGeometryの実計算をFoundationテストで検証する。先頭/末尾は直接page1/totalPagesへ指定し、中間ページを取得しない。通常更新・復帰は操作元なしとして、明示ページ送りのONを適用しない。

## プレイヤーの共有操作

設定パネルは実プレイヤーを所有せず、所有元へのクロージャで操作する。通常/全画面とも字幕とコメントの既存ビュー、時計、表示設定を使う。設定表示を理由に停止やビュー返却を行わず、シート終了はサブメニューやスワイプも含めナビゲーションコンテナから通知する。エンジン変更が必要な録画画質切替は、全画面とシートを閉じ、借用ビューを返し終えてから実行する。

## キャプチャ・リピート・再起動

キャプチャは共有VideoCaptureControllerが一要求ずつ処理する。VLCの例外はObjC境界、AVの一時出力は必ずremove。画像処理を背景へ分け、状態世代と再生所有者を確認してから保存する。AVの一時出力はフレーム取得直後に除去し、アップロード中には残さない。撮影は映像内の先頭2ボタンから行い、設定内に重複させない。

capture_save_mode / capture_caption_modeは本家と同じ値でSyncedSettingsStoreの差分同期へ追加する。保存先の既定はUploadServer、字幕はBoth。新規の端末キーを追加し既存接続先・認証・設定の保存形式は変えない。写真保存はPhotoKit addOnly、サーバー保存は既存認証request/sessionによるPOST /api/captures multipart image。サーバーのみでは写真APIを呼ばず、両方では各結果を通知する。保存開始後は不可逆処理を完了させ、新しい撮影は受け付けない。接続範囲は撮影時に控え、各アップロード前に照合する。

JPEG0.99に本家互換XPComment(tag40092/UTF-16LE JSON)・撮影時刻・Exifを付ける。CaptureJPEGはFoundationのみでTIFF/Exifを作り、CIでは実JPEGの復号と独立TIFF readerを使って検証する。番組開始基準の位置を記録し、カスタム命名マクロと字幕本文metadataは追加しない。

録画のリピートはVLC4のA-Bループで同じ描画出力を保ち、AVは終端シークを使う。設定は端末保存で、本家の録画既定ONに合わせる。終端おやすみと録画中を優先する。手動再起動は既存startPlayback/startStreamを再利用し、別のプレイヤー実装を増やさない。

## フェーズFの操作表示

下部は時間と撮影2種・実況・字幕・設定・PiP・全画面の1行と、映像下端に密着した独立シークに分ける。タブはSafe Area最下部に固定し、情報/コメントは映像直下から表示する。各Viewを作り直さず位置・選択を保つ。コメントの初回だけ追随を初期化し、再訪では既存の手動/自動追随状態を保つ。

通常の設定は映像下端からSafe Area下端に固定した子ナビゲーションで、表示中だけ下部タブを隠す。全画面は右側の幅を制限した子パネルを使い、下部操作を残す。タイトル/閉じるはナビバー、項目だけテーブルでスクロールし、サブメニューも同じ領域に置く。画質でエンジンが切り替わる場合は既存の全画面返却後の再構築を維持する。通常表示・PiP・認証・中継の所有関係は変更しない。

## 履歴保持件数

GeneralSettingsの数値は確定/キャンセルを持つ端末内ドラフトで、編集途中には保存しない。本家UI(min1/maxなし)に合わせ、正のIntを検証する。確定前にrequireFresh付きで最新値を確認できた場合だけ進み、減少や編集中の値変更は再確認する。設定の差分PUTは件数だけを更新し、履歴を直接削除しない。サーバーにCASがなく端末間の完全原子性はない。

新規履歴追加時だけWatchedHistoryRetentionが古い順/同時刻の元配列順に超過分を削除する。一度のsort+filterにして大量削減の二重走査を避け、不正要素の既存扱いを保つ。全設定GET/PUTと長いID指定URLの既存制約は残る。
